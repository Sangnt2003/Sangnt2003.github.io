6. Setup Application Load Balancer

In this step, we’ll create an Application Load Balancer to distribute traffic to our caching application and provide high availability.

Step 1: Create Target Group

Navigate to Target Groups

  1. Open the EC2 Console

  2. Click Target Groups in the left navigation

  3. Click Create target group

Configure Target Group

  1. Configure basic settings:

    • Target type: Instances
    • Target group name: caching-app-tg
    • Protocol: HTTP
    • Port: 3000
    • VPC: Select your caching-workshop-vpc

Configure Health Checks

  1. Configure health check settings:

    • Health check protocol: HTTP
    • Health check path: /health
    • Health check port: Traffic port
    • Healthy threshold: 2
    • Unhealthy threshold: 2
    • Timeout: 5 seconds
    • Interval: 30 seconds

  1. Click Next

Register Targets

  1. Select your application instance:

    • Find your caching-app-server instance
    • Select it and click Include as pending below

  1. Click Create target group

Step 2: Verify Target Health

Check Target Health

  1. Click on your target group to view details

  1. Go to the Targets tab and verify health status

It may take 1-2 minutes for the target to become healthy. The health check calls /health endpoint on port 3000.

Step 3: Create Application Load Balancer

Navigate to Load Balancers

  1. Click Load Balancers in the left navigation

  1. Click Create load balancer

Choose Load Balancer Type

  1. Select Application Load Balancer

  1. Click Create

Configure Basic Settings

  1. Configure load balancer settings:

    • Load balancer name: caching-app-alb
    • Scheme: Internet-facing
    • IP address type: IPv4

Configure Network Mapping

  1. Configure network settings:

    • VPC: Select your caching-workshop-vpc
    • Mappings: Select both public subnets from different AZs

Configure Security Groups

  1. Configure security groups:

    • Security groups: Select alb-sg
    • Remove the default security group

Configure Listeners

  1. Configure listeners and routing:

    • Protocol: HTTP
    • Port: 80
    • Default action: Forward to caching-app-tg

Step 4: Review and Create

Review Configuration

  1. Review all settings

  1. Click Create load balancer

Load balancer creation takes 2-3 minutes. The load balancer will show “Provisioning” status initially.

Step 5: Verify Load Balancer

Check Load Balancer Status

  1. Wait for the load balancer to become “Active”

  1. Note the DNS name for testing:
caching-app-alb-xxxxxxxxx.us-east-1.elb.amazonaws.com

Step 6: Test Load Balancer

Test Health Endpoint

  1. Test the load balancer using its DNS name:
# Test health endpoint through ALB
curl http://caching-app-alb-xxxxxxxxx.us-east-1.elb.amazonaws.com/health

Test Application Endpoints

  1. Test all application endpoints through the load balancer:
# Test product endpoint
curl "http://caching-app-alb-xxxxxxxxx.us-east-1.elb.amazonaws.com/product/PROD001?category=Electronics"

# Test products list
curl "http://caching-app-alb-xxxxxxxxx.us-east-1.elb.amazonaws.com/products"

# Test cache statistics
curl http://caching-app-alb-xxxxxxxxx.us-east-1.elb.amazonaws.com/stats

Step 7: Configure Additional Features

Enable Access Logs (Optional)

  1. Go to the Attributes tab of your load balancer

  1. Click Edit and enable access logs:

    • Access logs: Enabled
    • S3 location: Create or select S3 bucket

Configure Sticky Sessions (Optional)

  1. In your target group, go to Attributes tab:

    • Stickiness: Enabled
    • Stickiness type: Load balancer generated cookie
    • Stickiness duration: 1 day

Step 8: Monitor Load Balancer

CloudWatch Metrics

  1. Go to the Monitoring tab to view metrics

Key metrics to monitor:

  • RequestCount: Number of requests
  • TargetResponseTime: Response time from targets
  • HTTPCode_Target_2XX_Count: Successful responses
  • HTTPCode_Target_4XX_Count: Client errors
  • HTTPCode_Target_5XX_Count: Server errors

Set Up CloudWatch Alarms

  1. Create alarms for key metrics:
# High response time alarm
aws cloudwatch put-metric-alarm \
    --alarm-name "ALB-High-Response-Time" \
    --alarm-description "ALB response time is high" \
    --metric-name TargetResponseTime \
    --namespace AWS/ApplicationELB \
    --statistic Average \
    --period 300 \
    --threshold 1.0 \
    --comparison-operator GreaterThanThreshold \
    --evaluation-periods 2

Step 9: Test High Availability

Simulate Instance Failure

  1. Stop your EC2 instance to test failover:
# Stop the instance (simulate failure)
aws ec2 stop-instances --instance-ids i-xxxxxxxxxxxxxxxxx
  1. Check target group health

  1. Test load balancer response:
# This should return 503 Service Unavailable
curl http://caching-app-alb-xxxxxxxxx.us-east-1.elb.amazonaws.com/health

Restore Service

  1. Start the instance again:
# Start the instance
aws ec2 start-instances --instance-ids i-xxxxxxxxxxxxxxxxx
  1. Wait for target to become healthy again

Step 10: Document Load Balancer Configuration

Record the following information:

Load Balancer Information

  • Load Balancer Name: caching-app-alb
  • DNS Name: caching-app-alb-xxxxxxxxx.us-east-1.elb.amazonaws.com
  • Scheme: Internet-facing
  • Security Group: alb-sg
  • Target Group: caching-app-tg

Configuration Details

  • Listener: HTTP:80 → Forward to target group
  • Health Check: HTTP:3000/health
  • Health Check Interval: 30 seconds
  • Healthy Threshold: 2 consecutive checks

Troubleshooting Common Issues

Issue: Targets Showing Unhealthy

Possible Causes:

  • Application not responding on health check path
  • Security group blocking traffic
  • Instance not running

Solutions:

  • Verify application is running: pm2 status
  • Check health endpoint directly: curl localhost:3000/health
  • Verify security groups allow traffic on port 3000

Issue: 502 Bad Gateway Errors

Possible Causes:

  • Application crashed or not responding
  • Target group pointing to wrong port
  • Network connectivity issues

Solutions:

  • Check application logs: pm2 logs caching-app
  • Verify target group port configuration
  • Test direct instance connectivity

Issue: Load Balancer Not Accessible

Possible Causes:

  • Security group not allowing HTTP traffic
  • Load balancer in wrong subnets
  • DNS propagation delay

Solutions:

  • Verify ALB security group allows HTTP (port 80)
  • Ensure load balancer is in public subnets
  • Wait for DNS propagation (up to 5 minutes)

Performance Optimization

Connection Draining

  • Deregistration delay: 300 seconds (default)
  • Allows in-flight requests to complete before removing targets

Health Check Tuning

  • Faster detection: Reduce interval and threshold for quicker failover
  • Reduce false positives: Increase threshold for stable applications

Multiple Targets

  • Auto Scaling: Add multiple instances for higher availability
  • Cross-AZ: Distribute targets across availability zones

Next Steps

Your Application Load Balancer is now configured and tested! You have:

✅ Application Load Balancer distributing traffic
✅ Target Group with health checks configured
✅ High availability across multiple AZs
✅ Health monitoring with automatic failover
✅ CloudWatch metrics for performance monitoring
✅ Security groups properly configured

Load Balancer Benefits:

  • High availability: Automatic failover when instances fail
  • Scalability: Easy to add more instances behind the load balancer
  • Health monitoring: Continuous health checks ensure traffic goes to healthy instances
  • SSL termination: Can handle SSL/TLS encryption (when configured)

The load balancer DNS name will be used by CloudFront in the next step as the origin for our CDN distribution.
